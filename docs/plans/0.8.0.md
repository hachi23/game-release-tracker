# 0.8.0 plan: your data, ready to travel

Status: **proposed**. Nothing here is built yet. Each checkpoint below is one approved, reviewable commit (or a small group of commits) with its own tests, following [AGENTS.md](../../AGENTS.md).

## Why this release

0.7.0 made the app keep you informed (watchlist, date history, release alerts, tray). 0.8.0 makes your library **portable and measurable**:

- You can take your data out and bring it back in (CSV and JSON), and put your watched games on any calendar (.ics).
- The library gets ready for optional accounts and sync between devices in 0.9.0. Every row the user owns gets an id that never changes, a delete leaves a record, and every change is timestamped by device.
- Two features recruiters and users both understand straight away: a **Backlog** (what you mean to play next) and a **Stats** dashboard with a yearly goal.
- The repo enforces quality and performance in CI, not just by convention.

## Out of scope (0.9.0 and later)

Accounts, cloud sync, auto-update, Steam import, price alerts, a calendar subscription URL (it needs a server), mobile or web companions. See [Looking ahead](#looking-ahead).

## Ground rules for every checkpoint

1. **Spec first.** Before code, write the checkpoint's spec as a GitHub issue (problem, user story, rules, acceptance criteria, out of scope) and label it `ready-for-agent`. Run `/grilling` on it for any checkpoint marked **(grill)**.
2. **Domain language.** New terms go into `CONTEXT.md` in the same checkpoint (`/domain-modeling`). A decision that costs something gets an ADR.
3. **Test first.** Build each feature with `/tdd`: failing test, minimal code, refactor. Backend logic stays in pure modules where possible (like `buildYearInReview`), and frontend tests use `tests/frontend/fakeApiClient.ts`.
4. **Seams.** Routes stay thin, writes go through action and store modules, and list payloads stay light (AGENTS.md).
5. **Checks before every commit:** `npm rebuild better-sqlite3 && npm test && npm run typecheck && npm run build` (after checkpoint 1, also `npm run lint`).
6. **Packaged check** for anything a user sees: `npx electron-builder --linux dir` then `xvfb-run -a npm run smoke`.
7. **If a fix fails, revert or isolate it** before adding more patches (`/diagnosing-bugs` for anything not obvious).

## Checkpoint 2: sync-ready library (schema v22) (grill)

Invisible to users, but it's the base for import merging now and for sync in 0.9.0. **Needs an ADR** ("User-owned rows carry a stable id, a device timestamp and a delete record").

| Step | What | Done when |
|---|---|---|
| 2.1 | Inventory every **user-owned** table and field versus **IGDB-derived** data that can be fetched again. Write it into `CONTEXT.md` as a new term, *User-owned data*. Candidates: `completed_games` (personal fields only, see `completedPersonalFields.ts`), `user_release_state`, `manual_overrides`, `blocked_releases`, `completed_match_overrides`, `tracked_publishers`, sync settings, `year_in_review_settings`, `randomizer_picks`, preferences, and the new backlog. | Reviewed list in CONTEXT.md |
| 2.2 | Migration v22: a stable text id (UUID) on user-owned tables that lack one (for example `randomizer_picks`); a millisecond `changed_at` and a `changed_by_device` on user-owned rows; a `device_id` created once per library and stored in `settings`. The backup-before-upgrade path stays as it is. | Migration tests: fresh library, upgrade from v21 with sample data, upgrade from v21 with a real-looking library; an older app refuses v22 |
| 2.3 | **Delete records.** Deleting a Completed Game, a backlog entry or a User Override sets `deleted_at` instead of removing the row. Every read model (`completedReadModel.ts`, `releaseReadModel.ts`, Year in Review, Randomizer exclusions) filters them out. Hard deletes stay for **Remove sample data** and **Delete all app data**. Delete records older than a retention period can be purged at startup. | Read-model tests prove deleted rows never appear; the identity key can be reused after a delete |
| 2.4 | One write seam stamps `changed_at` and `changed_by_device` (in the store modules, not in routes), so no write path can forget. | A test fails if any store write skips the stamp |

## Checkpoint 3: export and import

**Needs a short ADR** for the portable file format (versioned JSON, user-owned data only, IGDB data fetched again after import). The same shape will be the sync change format in 0.9.0.

| Step | What | Done when |
|---|---|---|
| 3.1 | `apps/backend/src/portability/` (new module): `exportLibrary(db) → LibraryFile` (pure read, `formatVersion`, `exportedAt`, `deviceId`, user-owned rows only). Route `GET /api/export/library`. | Round-trip tests: export → import into an empty library → export gives the same file (ignoring `exportedAt`) |
| 3.2 | **Completed Library CSV export**: title, platform, finish date (with precision), rating, notes, IGDB id. Stable column order, UTF-8 with BOM for Excel, formulas escaped (a cell starting with `=`, `+`, `-` or `@` is quoted) to prevent CSV injection. | Tests with commas, quotes, newlines, emoji and formula-like titles |
| 3.3 | **Import with a preview.** `planImport(db, file) → ImportPlan` (pure: new / update / unchanged / conflict / invalid, with reasons), then `applyImport(db, plan)` in one transaction through the existing stores. JSON merges by stable id; CSV merges by **Identity Key**, so re-importing updates instead of duplicating. Ratings go through `completedRating.ts`. | Tests for every plan category; a failed apply changes nothing |
| 3.4 | Desktop: **Settings → Data** tab: *Export library (JSON)*, *Export finished games (CSV)*, *Import…*. Save and open dialogs in the desktop shell (like `saveImageIpc.ts`); the window never reads files itself. The preview screen shows counts and the first rows of each category before **Import**. | Frontend tests with the fake API client; smoke test opens the Data tab |
| 3.5 | Imported games without IGDB data queue for matching the same way a manually added game does (no extra IGDB calls during import itself). | Test: import then match uses the existing matcher |

## Risks

- **Delete records touch every read.** Mitigation: one shared "not deleted" filter in the read models and a test that lists every query over a user-owned table.
- **CSV from other tools is messy.** Mitigation: the preview never writes, and invalid rows are listed with reasons, not skipped silently.
- **Scope.** If time runs short, ship 1–4 as 0.8.0 and move Backlog and Stats to 0.8.1 rather than rushing them.

## Looking ahead

To discuss before planning in detail:

- **0.9.0, "Your library on every device":** optional account (OAuth in the system browser with PKCE, tokens in `safeStorage`), sync of user-owned data using the checkpoint 2 columns and the checkpoint 3 file format (outbox, push and pull by cursor, latest edit wins per field), a Devices list, account deletion, and auto-update from GitHub Releases. Reverses part of ADR 1, so it needs ADR 7 first.
- **1.0.0, "Ready for anyone":** signed builds, a stable public file format and API, a privacy policy, a full accessibility pass, a landing page and demo video, and a final architecture and documentation review.
